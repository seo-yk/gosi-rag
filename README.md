# 국가공무원 채용시험 FAQ RAG 평가 파이프라인

인사혁신처 사이버국가고시센터 FAQ 데이터로 만든 RAG 프로젝트입니다. 검색과 생성을 나눠 평가하고, 답변 품질이 낮을 때 원인이 어느 단계에 있는지 확인할 수 있게 했습니다.

1차 실험(2026.06~07) 뒤에 원본 데이터와 평가 방식에서 문제를 발견해, 데이터를 교정하고 평가셋을 다시 만든 다음 실험을 다시 했습니다(2026.11). 이 문서의 수치는 다시 한 실험(재실험)의 결과입니다. 재실험은 AI(Claude)와 함께 진행했고, 역할 분담은 3장에 적었습니다.

## 1. 프로젝트 목적

사이버국가고시센터 FAQ 289건으로 RAG 파이프라인을 만들고, 다음을 확인했습니다.

- 검색 단계와 생성 단계를 나눠 평가해 품질이 낮아지는 단계를 찾습니다.
- 청킹 방식, 임베딩 모델, 임베딩에 넣는 텍스트를 같은 평가셋으로 비교합니다.
- 생성 모델과 근거 조건(검색 결과를 주는 경우 / 정답 FAQ를 주는 경우)을 바꿔, 실패가 검색 때문인지 생성 때문인지 나눕니다.
- 자동 채점에 쓰는 LLM(채점기)이 사람과 얼마나 같게 판단하는지 확인한 뒤 사용합니다.

## 2. 주요 결과

- **원본 데이터 오류:** 원본 FAQ의 연번 100~200(101건)에서 본문이 한 칸씩 밀려, 각 행에 다음 질문의 답이 들어 있었습니다. 교정한 데이터로 실험을 다시 했고, 1차 결과는 사용하지 않았습니다.
- **검색:** 무료 오픈소스 모델 `bge-m3`가 한국어 특화 모델(`KURE-v1`), 상용 모델(`text-embedding-3-large`)과 5%p 넘는 차이가 없었습니다. 본문까지 임베딩한 경우가 제목만 임베딩한 경우보다 나았습니다.
- **생성:** `gpt-5.4-mini`의 합격률은 93.2%였습니다. 실패 10건 중 8건은 검색이 필요한 FAQ를 가져오지 못한 경우였고, 나머지 2건은 근거 FAQ가 있었는데 답을 피하거나 원문 문장을 반대로 해석한 경우였습니다. 필요한 FAQ가 검색된 140문항에서는 98.6%가 합격했습니다. 로컬 모델 `EXAONE 3.5 7.8B`는 같은 조건에서 69.6%였고, 실패 대부분은 근거 FAQ에 없는 내용을 답한 경우였습니다.
- **범위 밖 질문:** FAQ에 답이 없는 질문 10개는 두 생성 모델 모두 10개 전부 "근거를 찾을 수 없다"고 답했습니다.
- **채점기 검증:** 사람이 채점한 40문항과 비교해 채점기 후보 6개 중 하나를 골랐습니다. 로컬 소형 모델(4B, 7B)은 사람과의 일치율이 30~40%여서 쓰지 않았고, `gemini-3.8-flash`를 사용했습니다.
- **개선한 문제:** 실험 중 다음 세 가지를 찾아 고쳤습니다.
  - 인덱스를 만든 임베딩 모델과 질문에 쓰는 모델이 달라도 검색이 그대로 실행됐습니다. → 모델이 다르면 실행을 멈춥니다.
  - Ollama가 2,048토큰을 넘는 입력의 앞부분을 잘라낸 채 답변을 만들었습니다. → 컨텍스트를 8K로 늘리고, 입력이 한도에 닿으면 생성을 멈춥니다.
  - 채점 결과를 읽지 못한 문항이 불합격으로 집계됐습니다. → 다시 요청하고, 그래도 실패하면 `error`로 따로 셉니다.

## 3. 진행 방식과 역할

재실험(2026.11)은 AI(Anthropic의 Claude)와 함께 진행했습니다. 평가셋 초안 작업은 claude.ai 채팅에서, 코드 작성·실행과 문서 정리는 Claude Code에서 했습니다.

| 구분 | 본인 | AI(Claude) |
|---|---|---|
| 실험 방향 | 재실험 범위, 비교할 모델과 조건, 판단 기준(5%p), 채점 기준 변경(루브릭 v2.1) 결정 | 선택지와 근거 제시, 결정된 내용을 실험 설계로 정리 |
| 데이터 | 교정 결과와 병합·제외 결정 확인 | 원본과 교정본 비교, 교정·정리 스크립트 작성 |
| 평가셋 | 질문 57문항 직접 작성, AI 초안 91문항 검수, 정답 라벨과 기준 답변 확정(결정표), 질문 수정 승인 | 질문 91문항과 정답 라벨 초안 작성, 결정 내용 반영, 변경 이력 기록 |
| 코드·실행 | 결과 검토, 수정 방향 제시(예: 화면의 마크다운 표시, 파일·칼럼 이름) | 검색·생성·채점 코드 작성, 테스트, 실험 실행 |
| 사람 채점 | 채점기 검증용 채점 전부(40문항, 재검토 8문항, EXAONE 15문항, 재검토 7문항, 범위 밖 20문항) | 채점지 작성, 형식 점검(판단 내용은 검토하지 않음), 일치율 계산 |
| 해석·문서 | 결과 해석 검토와 결론 확정 | 결과 분석, 문서 초안 작성 |
| 비용 | API 키 발급과 비용 집행 | 호출 수와 비용 추정 |

- 사람 채점 결과는 AI가 바꾸지 않았습니다. 채점이 끝난 파일은 형식만 확인했고, 불일치 문항을 다시 볼지와 최종 판단은 본인이 정했습니다.
- 결정과 변경 이유는 `docs/experiment_log.md`에, 평가셋 변경 이력은 `evaluation/evalset/evalset_changes.csv`에 결정자와 함께 남겼습니다.

## 6. 실행 방법 (Docker)

Docker만 설치돼 있으면 데모 앱을 실행할 수 있습니다. 이미지에는 검색 실험에서 고른 구성(`BAAI/bge-m3`, 행 단위 청킹, 제목+본문 임베딩)의 인덱스와 임베딩 모델이 들어 있습니다. 답변 생성은 기본으로 OpenAI `gpt-5.4-mini`를 쓰므로 OpenAI API 키가 필요합니다.

```bash
git clone https://github.com/seo-yk/gosi-rag.git
cd gosi-rag
cp .env.example .env    # .env의 OPENAI_API_KEY에 키 입력
```

```bash
docker compose up --build
```

브라우저에서 `http://localhost:8501`을 엽니다. 처음 빌드할 때 패키지와 임베딩 모델(약 2.3GB)을 내려받아 시간이 걸립니다. API 키는 이미지에 들어가지 않고, 실행할 때 `.env`에서 읽습니다.

**로컬 생성 모델(Ollama)로 실행:** `.env`에서 `GENERATION_PROVIDER=ollama`, `GENERATION_MODEL=exaone3.5-7.8b-ctx8k`로 바꾼 뒤 Ollama 컨테이너를 함께 띄우고 모델을 준비합니다(약 5GB).

```bash
docker compose --profile ollama up --build -d
```

```bash
docker compose exec ollama ollama pull exaone3.5:7.8b
```

```bash
docker compose exec ollama ollama create exaone3.5-7.8b-ctx8k -f /modelfiles/exaone3.5-7.8b-ctx8k.Modelfile
```

Docker의 Ollama는 맥에서 GPU를 쓰지 못해 느립니다. 맥에 Ollama가 설치돼 있다면 `.env`에 `DOCKER_OLLAMA_BASE_URL=http://host.docker.internal:11434/v1`을 넣고 `docker compose up --build`로 앱만 실행해도 됩니다.

로컬(Python) 설치, 검색·생성·채점 실험 재현, 다른 모델·구성 조합 실험 방법은 `docs/experiment_log.md` 13장에 있습니다.

## 7. 실험 설계

| 단계 | 내용 | 기록 |
|---|---|---|
| **데이터** | 원본(289건)의 본문 밀림을 교정하고, 중복 2건 병합·본문 없는 1건 제외 → 검색 대상 286건 | `data/README.md` |
| **평가셋** | 1차의 검색용 50문항·생성용 60문항을 하나로 합침(v1.3): 148문항 + 범위 밖 10문항. FAQ 여러 개가 필요한 질문은 "모두 필요한 FAQ"와 "대신 써도 되는 FAQ"로 정답을 표시 | `evaluation/evalset/` |
| **검색** | 임베딩 모델 4개 × 3구성(행 단위·제목, 행 단위·제목+본문, 문장 단위·제목+본문) = 12조합 | Hit@1·3·5, MRR, 유형·작성자별 |
| **생성** | A: gpt-5.4-mini + 검색 결과 / B: gpt-5.4-mini + 정답 FAQ / C: EXAONE 7.8B + 검색 결과 | 자동 채점(근거성·정확성·필요한 내용 포함·답 회피), 범위 밖 질문은 사람 판정 |
| **채점기 검증** | 후보 6개를 사람이 채점한 40문항으로 비교, 불일치 문항 재검토, EXAONE 답변 15문항 추가 확인, 30문항 반복 채점 | 판정 일치율, Cohen's kappa |

148문항에서 1문항은 약 0.7%p입니다. 두 구성의 차이가 5%p 이내이면 "차이가 확인되지 않음"으로 판단했습니다.

## 8. 결과

### 8-1. 검색(Retrieval)

- **사용한 구성:** `BAAI/bge-m3` + 행 단위 청킹(FAQ 1개 = 청크 1개) + 제목·본문 임베딩

| 모델 | 구성 | Hit@1(단일 정답) | Hit@3 | Hit@5 | MRR(단일 정답) |
|---|---|---:|---:|---:|---:|
| e5-small | 행 단위, 제목 | 90.1% | 89.9% | 94.6% | 0.943 |
| **bge-m3** | **행 단위, 제목+본문** | **97.3%** | **94.6%** | **98.7%** | **0.985** |
| bge-m3 | 문장 단위, 제목+본문 | 98.2% | 94.6% | 98.7% | 0.991 |
| KURE-v1 | 행 단위, 제목+본문 | 95.5% | 94.6% | 99.3% | 0.975 |
| text-embedding-3-large | 행 단위, 제목+본문 | 92.8% | 91.9% | 98.7% | 0.959 |

- 5%p를 넘은 모델 간 차이는 bge-m3와 e5-small 사이 하나였습니다. bge-m3, KURE-v1, text-embedding-3-large 사이에는 차이가 확인되지 않았습니다.
- 4개 모델 모두 제목+본문 임베딩이 제목만 임베딩한 경우보다 높았습니다. 1차의 결론("제목만 임베딩하는 편이 낫다")과는 반대이며, 원본 데이터 교정이 원인일 수 있습니다.
- 문장 단위 청킹과 행 단위 청킹은 차이가 확인되지 않았습니다. FAQ 본문이 평균 255자로 짧습니다.
- FAQ 2개 이상이 필요한 질문(37문항)은 1위 결과 하나로는 정답을 채울 수 없어 Hit@1이 항상 0입니다. 그래서 Hit@1과 MRR은 정답 FAQ가 하나인 111문항 기준으로 비교했습니다.

> 전체 12조합 결과: `results/retrieval_v1.3/`, 해석과 편향 점검: `docs/retrieval_pipeline.md`

### 8-2. 생성(Generation)

| 조건 | 생성 모델 | 근거 | 합격 | 범위 밖 질문 차단 |
|---|---|---|---:|---:|
| A | gpt-5.4-mini | 검색 결과 3개 | 93.2% (138/148) | 10/10 |
| B | gpt-5.4-mini | 정답 FAQ | 98.0% (145/148) | - |
| C | EXAONE 3.5 7.8B | 검색 결과 3개 | 69.6% (103/148) | 10/10 |

- A의 실패 10건 중 8건은 검색이 필요한 FAQ를 가져오지 못한 문항이었고, 모두 FAQ 2개 이상이 필요한 질문이었습니다(37문항 중 8건). 이 중 5건은 빠진 부분을 "확인할 수 없다"고 답했고, 1건은 그 부분을 빠뜨렸고, 2건은 근거 없이 틀린 내용을 답했습니다.
- 나머지 2건은 필요한 FAQ가 검색됐는데도 실패했습니다.
  - 122번(예비군 훈련 불참 벌금): FAQ는 임용 제한 대상을 나열하고 있어 "해당하지 않는다"고 답할 수 있었지만, 모델은 "명시되어 있지 않아 확인할 수 없다"고 답했습니다.
  - 153번(답안지 과목 순서): FAQ 원문 "순서를 바꾸어 표기하여도, 문제책 순서대로 채점이 되므로 착오 없으시기 바랍니다"를 "바꿔도 된다"로 해석했습니다. 원문은 바꾸면 오답이 될 수 있으니 주의하라는 뜻입니다. B도 같은 해석을 했는데 채점기는 B의 답을 합격으로 판정했습니다(채점기가 놓친 1건, 빼면 B 97.3%).
- 필요한 FAQ가 검색된 140문항에서 A의 합격률은 98.6%로, 정답 FAQ를 준 B(98.0%)와 비슷했습니다.
- C는 A와 같은 검색 결과와 같은 프롬프트를 받았고, 합격률이 23.6%p 낮았습니다. 필요한 FAQ가 검색된 경우에도 37건이 실패했고, 그중 36건은 근거 FAQ에 없는 내용(존재하지 않는 URL, FAQ에 없는 규정 등)을 포함했습니다.
- 범위 밖 질문 10개는 A와 C 모두 근거가 없다고 답했고, FAQ에 없는 수치나 사실을 답한 경우는 없었습니다.

> 생성 결과와 실패 원인 분석: `docs/generation_results.md`, 원본: `results/generation_v1.3/`

### 8-3. 채점기 검증

| 채점기 후보 | 사람 채점 40문항과 판정 일치 | kappa |
|---|---:|---:|
| gemma3:4b (로컬) | 40.0% | 0.10 |
| qwen2.5:7b (로컬) | 30.0% | 0.06 |
| **gemini-3.8-flash (사용)** | 90.0% → 재검토 후 **95.0%** | 0.45 → **0.64** |

- 로컬 모델 2개는 사람이 합격으로 본 답변의 대부분을 불합격으로 판정했습니다.
- EXAONE 답변 15문항에서는 처음에 사람과 8문항만 일치했습니다(kappa 0.12). 채점기가 지적한 내용을 사람이 근거 FAQ와 대조해 다시 판단한 뒤에는 14문항이 일치했습니다(kappa 0.87). 처음 사람 채점에서 근거 FAQ에 없는 내용을 놓친 경우가 있었습니다.
- 같은 문항을 다시 채점했을 때 30문항 중 29문항의 판정이 같았습니다.
- 사람 채점자는 1명이며, 재검토 전과 후의 수치를 모두 기록했습니다.

> 채점기 선정 과정과 재검토 기록: `evaluation/judge_calibration/`

### 8-4. 정리

- 답변 품질 문제는 검색과 생성을 나눠서 보고, 정답 FAQ를 준 조건과 비교해야 원인을 구분할 수 있었습니다.
- 모델을 비교하기 전에 데이터와 평가셋을 먼저 확인해야 했습니다. 원본 데이터 오류가 1차 실험의 결론에 영향을 주었습니다.
- 자동 채점 결과는 사람 채점과 비교해 확인한 뒤 사용했습니다. 사람 채점도 채점기의 지적을 근거와 대조하는 과정에서 수정됐습니다.

## 9. 1차 실험과의 관계

1차 실험(검색 Hit@1 90.2%, 사람·자동 채점 일치율 91.67%)의 결과는 다음 이유로 다시 사용하지 않습니다. 1차 파일은 `archive/experiment-v1/`에, 당시 저장소 상태는 태그 `experiment-v1`에 있습니다.

1. 원본 FAQ의 연번 100~200 본문이 한 칸씩 밀려 있었습니다.
2. 검색 평가 문항 수가 모델마다 달랐습니다(51·50문항).
3. 검색용(50)과 생성용(60) 평가셋이 따로 있었습니다.
4. 상위 3개만 검색한 결과로 Hit@5를 계산해, Hit@3과 Hit@5가 항상 같았습니다.
5. 문단 단위·파일 단위 청킹은 실제로 비교가 되지 않았습니다(본문에 빈 줄이 없고, 파일 단위는 청크가 1개).
