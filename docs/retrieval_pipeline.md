# 검색 파이프라인과 평가 설계

작성일 2026-11-12. 재실험(평가셋 v1.3, FAQ faq-v2) 기준의 문서 검색 과정과 실험 설계, 편향 점검 내역을 기록한다. 결과 수치는 재실험 후 별도로 추가한다.

## 1. 전체 흐름

```text
[데이터]  data/faq_v2.csv (286건: 연번, 제목, 본문)
   │
   ▼  src/indexing.py
[인덱싱]  로드·검증 → 청킹(row / sentence) → 임베딩 입력 구성(title / title_body)
          → 임베딩(passage) → L2 정규화 → FAISS IndexFlatIP 저장 (+ metadata.json, manifest.json)
   │
   ▼  src/retrieval.py
[검색]    질문 임베딩(query) → L2 정규화 → 내적(=코사인) Top-N 청크
   │
   ▼  evaluation/scripts/evaluate_retrieval.py
[채점]    청크 → FAQ 연번 중복 제거 → Top-5 FAQ → 그룹 채점(Hit@K, Group Recall@K, MRR)
          → 전체 / 단일 그룹 / 유형별 / 작성자별 요약, 문항별 상세, 범위 밖 유사도 기록
```

|---|---|---|---|

| 검색 대상 | `data/faq_v2.csv` | 286 | 근접 중복 2건 병합(94→280, 152→250), 본문 없는 99 제외, FAQ 15 반복 본문 정리 |

- 본문 길이: 평균 255자, 중앙값 236자, 500자 초과 8건. 평균 2.4문장이고, 문단을 나누는 빈 줄은 하나도 없다.

## 3. 인덱싱 (`src/indexing.py`)

### 3-1. 로드와 검증

`연번`, `제목`, `본문` 열이 모두 있어야 한다. 빈 연번, 빈 제목·본문, 중복 연번이 있으면 중단한다.

### 3-2. 청킹: 문서를 어떤 단위로 자를 것인가

| 모드 | 단위 | 청크 수(faq-v2) | 실험 사용 |
|---|---|---|---|
| `row` | FAQ 1개 = 청크 1개 | 286 | ✓ |
| `sentence` | 본문 문장 1개 = 청크 1개. 청크마다 FAQ 제목 유지 | 634 (FAQ당 평균 2.2) | ✓ |
| `paragraph` | 빈 줄 기준 문단 | 286 | ✗ 교정본에 빈 줄이 없어 `row`와 완전히 같음 |
| `file` | 전체 FAQ = 청크 1개 | 1 | ✗ 어떤 질문에도 같은 문서 하나만 나와 비교가 성립하지 않음 |

`sentence` 규칙:

- 한글·닫는 괄호·따옴표 뒤의 `.`, `?`, `!`에서만 자른다. 그래서 `2007.12.31.` 같은 날짜 안에서는 자르지 않는다.
- 20자 미만 조각은 앞 문장에 붙인다.
- 청크마다 원래 FAQ의 제목을 유지한다. `title_body`로 임베딩하면 `제목: …\n본문: (문장)`이 되어, 제목이 문맥 머리말 역할을 한다.
- 검증하려는 가설: 1차 실험 해석에 "세부 키워드가 본문에만 있어 회수되지 않았다"가 있었다. 문장 단위로 자르면 본문 세부 내용이 질문과 직접 비교되므로 이 문제가 줄어드는지 본다.
- 한계: 가장 긴 FAQ(1,294자)는 문장 경계 패턴이 맞지 않아 통째로 1청크가 된다.

### 3-3. 임베딩 입력: 청크를 어떤 텍스트로 벡터화할 것인가

청킹과는 다른 축이다.

| 모드 | 입력 텍스트 | 비고 |
|---|---|---|
| `title` | FAQ 제목(질문 형태) | 1차 최종 조합. `sentence`와는 조합하지 않는다. 청크마다 제목이 같아 같은 벡터가 반복되기 때문 |
| `title_body` | `제목: {제목}\n본문: {본문 또는 문장}` | |

### 3-4. 임베딩

- 같은 모델로 문서(`passage`)와 질문(`query`)을 임베딩한다.
- e5 계열은 학습 규칙에 따라 `passage: `, `query: ` 접두어를 붙인다. bge-m3, KURE 등 다른 모델에는 붙이지 않는다.
- OpenAI 모델은 한 번의 요청으로 문서 전체를 임베딩한다(최대 634개 입력).
- 입력 길이: e5-small의 최대 길이는 512토큰이다. `title_body` 기준으로 512토큰을 넘는 것은 `row` 3건, `sentence` 1건이라 잘림의 영향은 작다. bge-m3와 KURE는 8192토큰까지 받는다.

### 3-5. 인덱스와 저장

- 모든 벡터를 L2 정규화한 뒤 `faiss.IndexFlatIP`(내적)에 넣는다. 정규화된 벡터의 내적은 코사인 유사도다.
- Flat 인덱스는 근사 없이 전수 비교하므로 결과가 결정적이다.
- 저장 경로: `index/faq_v2/<모델 이름>/<청킹>/<제공자>/`. 모델 이름은 `EMBEDDING_MODEL`의 마지막 부분이다(예: `nlpai-lab/KURE-v1` → `kure-v1`)
  - `{title,title_body}.faiss`
  - `metadata.json`: 청크별 FAQ 연번, 제목, 본문, 청크 ID(`row-12`, `row-12-s2` 등)
  - `manifest.json`: 원천 CSV 경로와 sha256, 원천 행 수, 청크 수, 임베딩 모델, 생성 시각

## 4. 검색 (`src/retrieval.py`)

1. 질문을 `query` 역할로 임베딩하고 L2 정규화한다.
2. FAISS에서 내적이 큰 순으로 청크를 가져온다.
3. 결과는 청크와 유사도 점수이고, 각 청크는 원래 FAQ 연번(`resolved_row_id`)을 갖는다.

## 5. 채점 (`evaluation/scripts/evaluate_retrieval.py`)

### 5-1. 평가셋

- 본 평가셋: `evaluation/inputs/evalset_v1.3.jsonl`의 keep 148문항. 필수 그룹이 1개인 111문항과 복수근거 37문항이다.
- 범위 밖: `evalset_out_of_scope_v1.3.jsonl`의 10문항
- 정답 형식 `required_faqs`: 바깥 목록은 AND, 안쪽 목록은 OR. 예: `[[78], [272, 251]]`는 78, 그리고 272 또는 251.
- 보조 FAQ(`supporting_faqs`)는 어떤 지표에도 넣지 않는다.

### 5-2. 평가 전 확인

| 확인 | 실패 시 |
|---|---|
| 인덱스의 `manifest.json`이 있는가 | 중단(인덱스 재생성 안내) |
| 인덱스를 만든 모델과 질문 임베딩 모델이 같은가 | 중단(앱도 같은 검사를 한다) |
| 모든 정답 FAQ가 인덱스에 있는가 | 중단 |
| 라벨 형식(`validate_labels.py`) | 실행 전 별도 검증, 오류 0건 |

### 5-3. 순위 만들기

1. 질문마다 청크 50개(`depth 5 × 10`)를 검색한다.
2. FAQ 연번 기준으로 중복을 제거한다. FAQ마다 가장 높은 순위의 청크만 남긴다.
3. 서로 다른 FAQ 5개로 순위를 만든다. 5개를 채우지 못하면 경고를 출력한다.
4. 한 번 검색한 순위로 @1·@3·@5를 함께 계산한다.

같은 모델의 여러 조합은 질문 벡터를 캐시해 함께 쓴다. 그래서 조합 사이에 질문 쪽 조건이 완전히 같다.

### 5-4. 지표

| 지표 | 정의 | 대상 |
|---|---|---|
| Hit@K | 모든 필수 그룹에서 FAQ가 1개 이상 Top-K에 들면 1 | 148 |
| Group Recall@K | 충족된 그룹 수 ÷ 전체 그룹 수 | 148 |
| MRR | 그룹 내 FAQ 중 가장 높은 순위의 역수 | 단일 그룹 111 |
| 범위 밖 | Top-1 FAQ와 유사도, Top-5를 기록만 한다(임곗값 없음). 차단 여부는 생성 단계에서 사람이 판정 | 10 |

요약은 다음 묶음(`subset`)별로 낸다.

- `전체`
- `단일 그룹 전체`
- `유형: 원문유사·일상표현·조건형·복수근거`
- `작성: 본인·Claude`

### 5-5. 결과 파일

파일 이름 끝에 모델 이름이 붙는다(`--run-name`으로 바꿀 수 있다). 모델 비교표는 `build_retrieval_comparison.py`로 만든다.

| 파일 | 내용 |
|---|---|
| `output/retrieval_summary_<run>.csv` | 조합 × 묶음별 지표. 평가셋 이름, 원천 CSV 해시, 청크 수, 모델 포함 |
| `output/retrieval_details_<run>.csv` | 문항별 검색 FAQ 순위와 @1·@3·@5 적중 |
| `output/retrieval_out_of_scope_<run>.csv` | 범위 밖 문항의 Top-1 FAQ·유사도와 Top-5 |

## 6. 실험 설계

청킹·임베딩 입력 3가지 × 임베딩 모델 4개 = 12조합

| | `row` × `title` | `row` × `title_body` | `sentence` × `title_body` |
|---|---|---|---|
| `intfloat/multilingual-e5-small` | ✓ | ✓ | ✓ |
| `BAAI/bge-m3` | ✓ | ✓ | ✓ |
| `nlpai-lab/KURE-v1` | ✓ | ✓ | ✓ |
| `text-embedding-3-large` | ✓ | ✓ | ✓ |

모델 선정 이유:

| 모델 | 역할 | 이유 |
|---|---|---|
| multilingual-e5-small | 경량 다국어 기준선 | 1차 최고 성능 모델. 1차와 이어서 비교 |
| bge-m3 | 다국어 대형 | KURE의 바탕 모델. 한국어 추가 학습의 효과만 따로 보기 위한 대조군 |
| KURE-v1 | 한국어 특화 | 데이터가 모두 한국어라서. 모델 카드 기준 한국어 검색 벤치마크 상위권(자체 보고) |
| text-embedding-3-large | 상용 API | 상용 모델과의 비교. 같은 계열의 3-small은 1차 결과로 대체 |

## 7. 편향·무결성 점검

### 7-1. 1차 실험에서 발견해 고친 것

| 문제 | 영향 | 조치 |
|---|---|---|
| 원본 FAQ 연번 100~200(101건)의 본문이 한 칸 밀림 | `title_body` 검색과 생성 근거가 다른 질문의 답이었다 | 교정본 사용(`data/CHANGES_faq.md`) |
| 검색 평가 문항 수가 모델마다 다름(e5 51, OpenAI 50) | 모델 간 비교가 같은 조건이 아니었다 | 모든 모델이 같은 148문항. 결과에 평가셋 이름과 문항 수 기록 |
| 검색용(50)과 생성용(60) 평가셋이 따로 있음 | 단계 간 비교 불가 | 단일 평가셋 v1.3 |
| Top-3로 검색한 결과로 Hit@5를 계산 | Hit@3과 Hit@5가 항상 같았다 | 한 번에 5개를 검색해 @1·@3·@5 계산 |
| `paragraph`·`file` 청킹이 실질적 비교가 아님 | 청킹 비교가 성립하지 않았다 | 의미 있는 `sentence` 청킹 추가 |

### 7-2. 재실험 준비 중 발견해 고친 것

| 문제 | 영향 | 조치 |
|---|---|---|
| e5 전용 접두어가 모든 로컬 모델에 붙음 | bge-m3·KURE 성능이 부당하게 낮아질 수 있음 | e5 계열에만 적용, 테스트로 고정 |
| 인덱스와 질문 임베딩 모델이 달라도 오류가 없음 | 차원이 같은 모델(bge-m3·KURE 1024차원)끼리는 결과가 조용히 틀린다 | `manifest.json` 대조 후 중단 |
| 문장 청킹 시 같은 FAQ의 청크가 Top-K를 채움 | 순위 왜곡, 다른 FAQ가 밀려남 | FAQ 연번 기준 중복 제거 후 채점 |
| 인덱스 폴더가 모델과 무관하게 하나라서, 여러 모델의 인덱스가 섞이거나 앱이 다른 모델 인덱스를 읽을 수 있음 | 실험 결과와 생성 근거가 다른 모델의 인덱스에서 나올 수 있음 | 인덱스 폴더를 모델 이름으로 자동 결정, 앱에도 manifest 대조 추가 |
| 인덱스 생성 기본값이 OpenAI·로컬 제공자를 함께 쓰면서 모델 이름은 하나만 받음 | 기본 실행이 실패(OpenAI에 로컬 모델 이름으로 요청) | 제공자 하나(`EMBEDDING_PROVIDER`)만 쓰도록 변경 |
| 조합마다 질문을 다시 임베딩 | 질문 쪽 조건이 미세하게 다를 수 있고 API 호출도 늘어남 | 모델별 질문 벡터 캐시 |
| 복수근거 문항은 Hit@1이 구조적으로 0 | 전체 Hit@1의 최댓값이 75.0%라서 1차(90.2%)와 직접 비교하면 오해 | `단일 그룹 전체` 행을 따로 보고 |

### 7-3. 남아 있는 편향과 읽는 법

| 항목 | 측정값 | 해석과 대응 |
|---|---|---|
| 질문과 정답 FAQ 제목의 표현 겹침 | 글자 2-gram 겹침 평균: 원문유사 0.63, 조건형 0.53, 일상표현 0.40, 복수근거 0.29 | 원문유사는 설계상 제목과 가깝다. 제목 임베딩(`title`)에 유리하므로 유형별 수치를 함께 본다 |
| 질문 작성자에 따른 겹침 | Claude 초안 0.53(91문항), 본인 0.34(57문항). 겹침 0.8 이상: Claude 12, 본인 0 | Claude 초안이 FAQ 표현에 더 가깝다. 검수표 P열에서 그대로 베낀 질문 7건을 고쳤지만 차이가 남아 있다. 작성자별 행으로 확인한다. 작성자마다 유형 구성이 달라 두 요인이 섞여 있다 |
| 라벨 검수자 1인 | | 라벨 초안은 Claude, 확정은 본인. 결정 이력은 `evaluation/inputs/CHANGES.csv` |
| 원본 FAQ 사이의 상충 | 사전등록 경로가 288·289·247에서 다름 | 원본 그대로 둔다. 생성 평가에서 정답 처리 방식 결정 필요 |
| 범위 밖 유사도 점수 | | 모델마다 점수 분포가 달라 모델 사이 절댓값 비교는 의미가 없다. 같은 모델 안에서 본 평가셋 Top-1 점수와 비교한다 |
| 결정성 | | Flat 인덱스는 전수 비교라 결정적이다. 로컬 GPU(MPS)의 부동소수 차이로 극히 드물게 순위가 바뀔 수 있다 |

### 7-4. 생성 단계로 넘길 주의

- `sentence` 청킹을 생성에 쓰면, 지금 앱은 검색된 문장만 근거로 넘긴다. 같은 FAQ의 문장이 중복될 수도 있다. 생성 단계에서 `sentence`를 고르면, 검색은 문장으로 하고 근거는 원래 FAQ 전체로 넘기는 처리(parent document)가 필요하다. 아직 구현하지 않았다.
- 범위 밖 10문항은 자동 평가에서 빠지고 사람이 판정한다(`evaluation/inputs/README.md` 채점 규칙).

### 9-1. 해석

1. **모델:** 5%p를 넘는 모델 차이는 `row × title_body`에서 bge-m3와 e5-small 사이(Hit@1 단일 97.3% 대 91.9%, +5.4%p) 하나뿐이다. bge-m3, KURE-v1, text-embedding-3-large 사이에는 어느 조합에서도 차이가 확인되지 않는다. 한국어 추가 학습(KURE)과 상용 API(3-large)가 이 데이터에서 다국어 대형 오픈소스 모델(bge-m3)보다 낫다는 근거는 없다.
2. **임베딩 입력:** 12개 비교 중 대부분에서 `title_body`가 `title`보다 같거나 높다. 5%p를 넘은 것은 bge-m3(Hit@1 단일 +5.4%p)뿐이다. 1차 실험의 "제목만 임베딩이 낫다"는 결론은 이번 데이터에서 재현되지 않았다. 원본 본문 밀림(연번 100~200)을 교정한 것이 한 원인일 수 있으나 이 실험만으로는 단정할 수 없다.
3. **청킹:** `sentence`와 `row`(둘 다 `title_body`)는 모든 모델에서 전체 지표 차이가 확인되지 않는다. 복수근거 37문항의 Hit@3은 e5-small에서 `row × title` 62.2% → `sentence × title_body` 83.8%로 올랐다. 다만 37문항(1문항 ≈ 2.7%p)이고 본문 추가 효과와 섞여 있어, "문장 청킹이 복수 근거 회수에 도움이 될 수 있다"는 가설 수준으로 본다. 문서가 짧아서(평균 255자) FAQ 1개를 청크 1개로 두어도 충분했다.
4. **작성자 편향:** 12개 조합 모두에서 Claude가 쓴 질문의 Hit@3이 본인이 쓴 질문보다 높다(차이 2.2~11.0%p). 7-3의 "Claude 질문이 FAQ 제목과 더 겹친다"는 측정과 같은 방향이다. 실제 사용자 질문에 대한 성능은 본인 작성 문항(57문항) 쪽에 더 가깝다고 보고 함께 보고한다.
5. **1차와의 관계:** 1차 Hit@1 90.2%(51문항, 원본 데이터, 정답 1개)와 이번 e5-small `row × title`의 Hit@1(단일) 90.1%는 숫자가 비슷하다. 그러나 평가셋, 데이터, 채점 방식이 달라 직접 비교하지 않는다.
