## 1. 배경

- 저장소: `gosi-rag` (국가공무원 채용시험 FAQ 289건 기반 RAG 평가 파이프라인)
- 1차 실험(2026.06~07)의 결과는 다시 쓰지 않는다. 이유는 세 가지다.
  - 원본 FAQ 데이터에 제목과 본문이 어긋난 구간이 있었다.
  - 검색 평가의 문항 수가 모델마다 달랐다(e5 51문항, OpenAI 50문항).
  - 검색용(50)과 생성용(60) 평가셋이 따로 있었다.
- 목표: 교정본 FAQ와 단일 평가셋 v1.2로 파이프라인을 다시 돌리고 개선한다.
- 사용자의 목적은 취업 포트폴리오다. 결과 수치는 면접에서 근거를 설명할 수 있어야 한다. 그래서 출처, 검수자, 변경 이력을 빠짐없이 남긴다.

## 4. 평가셋 스키마 (JSONL, 문항당 한 줄)

```json
{
  "question_id": "q052",
  "status": "keep",
  "question": "응시표를 잃어버렸고 ... 그냥 가도 되나요?",
  "intent": "...",
  "question_type": "복수근거",
  "evidence_type": "multi",
  "multi_intent": true,
  "expected_behavior": "answer",
  "required_groups": [{"faq_ids": [78]}, {"faq_ids": [272, 251]}],
  "supporting_faq_ids": [77],
  "reference_answer": "...",
  "author": "직접 작성(v1.0)",
  "label_author": "Claude 초안",
  "reviewer": "본인",
  "eval_set_version": "v1.2"
}
```

- `status`: `keep` 또는 `exclude`. `exclude` 문항은 파일에 남기되 평가에서 뺀다.
- `evidence_type`: 그룹이 2개 이상이면 `multi`, 1개이면 `single`, 범위 밖이면 `none`.
- `author`: 검수표의 `출처` 열 값을 그대로 쓴다(`초안(Claude)` 또는 `직접 작성(v1.0)`).
- `reviewer`: 사용자가 결정을 입력한 문항만 `본인`. 결정이 없는 문항은 빈 값으로 둔다.
- `required_facts`는 이번 범위가 아니다. 필드를 만들지 않는다.

범위 밖 문항은 `eval_out_of_scope_v1.2_draft.jsonl`의 형식을 따른다. `pass_rule`을 지우지 않는다.

## 5. 채점 규칙

| 지표 | 정의 | 대상 |
|---|---|---|
| Hit@K | 모든 그룹에서 FAQ가 1개 이상 Top-K 안에 있으면 1 | 148문항 |
| Group Recall@K | 충족된 그룹 수 ÷ 전체 그룹 수 | 148문항 |
| MRR | 그룹 내 FAQ 중 가장 높은 순위의 역수 | `single` 문항만 |
| 범위 밖 차단 | 근거 없음을 밝히면 통과. 건수로 보고한다(예: 10문항 중 9문항) | 10문항 |

- 보조 FAQ(`supporting_faq_ids`)는 어떤 지표에도 넣지 않는다.
- 모든 임베딩 모델을 같은 148문항으로 평가한다. 결과 파일에 문항 수와 평가셋 버전을 기록한다.
- 유형별(`question_type`) 수치를 함께 낸다.
- 148문항에서 1문항은 약 0.7%p다. 두 구성의 차이가 5%p 이내이면 "차이가 확인되지 않음"으로 보고한다.
- 범위 밖 문항은 Top-1 유사도 점수를 함께 기록한다. 현재 코드에는 유사도 임곗값이 없으므로 임곗값은 적용하지 않고 측정만 한다.

## 7. 작업 순서

각 작업은 별도 커밋으로 남긴다. 브랜치 이름은 `evalset-v1.2`를 쓴다. 커밋 메시지는 저장소 관례(`feat:`, `docs:`, `refactor:`, `test:`, `chore:`)를 따른다.

### 작업 1. 검색 대상 데이터 `faq-v2` 만들기

- 입력: `handoff/faq_corrected.csv`, `handoff/faq_merge_map.csv`, 결정표 `5_기타확인` 시트
- 처리
  - 병합표의 `removed_id`(94, 152)를 제거한다.
  - FAQ 15의 반복된 본문을 한 번만 남긴다(결정표에서 "확정"일 때).
  - FAQ 99는 결정표의 선택에 따른다. "본문 보완"이면 사용자에게 본문을 받는다. "제외"이면 제거한다.
- 출력: `data/faq_v2.csv`, `data/faq_merge_map.csv`, `data/CHANGES_faq.md`(원본 대비 바뀐 내용과 사유)
- 완료 기준: 행 수가 예상과 같다(287, FAQ 99를 제외하면 286). `data/faq.csv`는 변경되지 않았다.

### 작업 2. 평가셋 v1.2 만들기

- 입력: 검수표, 라벨 초안, 범위 밖 초안, 결정표
- 처리 순서
  1. 검수표와 라벨 초안을 `question_id`로 합친다.
  2. 결정표를 반영한다.
     - `1_필수라벨`: 수락이면 라벨 초안 유지, 기각이면 검수표의 기존 필수·보조로 되돌림, 수정이면 G열 내용 적용
     - `2_기준답변`: 수락이면 수정안, 기각이면 현재 답변, 수정이면 H열 문장
     - `3_유형재분류`: F열 유형 적용
     - `4_범위밖`: 수락이면 유지, 기각이면 `status`를 `exclude`로, 수정이면 F열 문구
     - `5_기타확인`: q122의 보조 FAQ를 선택대로 적용
  3. 결정 칸이 빈 행은 반영하지 않는다. 목록으로 보고하고 사용자 답을 기다린다.
  4. 검수표 P열에 사용자가 적은 수정안 16건(우선순위 1·2 문항)을 반영한다. P열은 방향만 적혀 있으므로(예: "FAQ 제목을 그대로 베낌 (아버지 -> 부모님)") 문항별로 수정 전·후 문장을 표로 제안하고, 사용자 승인을 받은 뒤 적용한다.
  5. 라벨 초안의 "보조만 변경" 29문항은 그대로 적용한다. 보조 FAQ는 채점에 쓰이지 않는다.
- 출력
  - `evaluation/inputs/evalset_v1.2.jsonl` (150줄, 그중 `keep` 148)
  - `evaluation/inputs/evalset_out_of_scope_v1.2.jsonl`
  - `evaluation/inputs/CHANGES.csv` (열: `question_id`, `field`, `before`, `after`, `reason`, `decided_by`)
  - `evaluation/inputs/README.md` (문항 수, 유형 분포, 작성자 분포, 검수자 1인, 라벨 초안은 Claude가 쓰고 사용자가 확정했다는 사실, 병합과 제외 내역)
- 완료 기준: `validate_labels.py`가 `data/faq_v2.csv` 기준으로 오류 0건. 사용자가 최종 확인하면 태그 `evalset-v1.2`를 붙여 동결한다. 동결 후 라벨을 바꾸려면 버전을 올린다.

### 작업 3. 평가 스크립트 수정

- `evaluation/scripts/evaluate_retrieval.py`가 `evalset_v1.2.jsonl`을 읽고 5장의 지표를 내도록 고친다.
- 데이터 경로를 `data/faq_v2.csv`로 바꿀 수 있게 한다. 기본값을 바꿀지는 사용자에게 묻는다.
- 범위 밖 문항은 Top-1 유사도와 검색된 FAQ 번호를 기록한다.
- `generate_generation.py`, `evaluate_generation.py`는 새 평가셋의 `question`, `reference_answer`를 읽도록 입력부만 고친다. 평가 루브릭은 이번에 바꾸지 않는다.
- 그룹 채점 로직에 단위 테스트를 추가한다. 최소 사례: 단일 그룹, 대체 정답으로 적중, 복수 그룹 중 일부만 적중, 보조만 검색된 경우(오답).
- 완료 기준: `pytest` 전체 통과.

### 작업 4. 재실험

- 사용자 승인 전에는 실행하지 않는다. 임베딩과 생성에 유료 API 호출이 들어간다.
- 승인 시 실행 계획(모델, 조합 수, 예상 호출 수)을 먼저 보고한다.
- 1차의 `file` 청킹과 Top-K 3/5 비교는 변별력이 없었다. 그대로 반복할지 사용자에게 묻는다.

## 8. 지켜야 할 것

- 라벨, 기준 답변, 질문 문구를 사용자 결정 없이 바꾸지 않는다. 문제를 발견하면 수정 전·후와 사유를 표로 제안한다.
- 사용자에게 검토를 요청할 때는 파일 이름, 시트나 열, 판단 기준, 입력할 값을 함께 적는다.
- `data/faq.csv`와 `output/`의 1차 결과 파일을 지우거나 덮어쓰지 않는다.
- README의 1차 수치(Hit@1 90.2%, 일치율 91.67% 등)는 재실험 결과가 나오기 전에는 고치지 않는다. 재실험 뒤 한 번에 교체한다.
- 2차 이터레이션(`docs/iterations/v2/`)의 구현은 이번 범위가 아니다.

## 9. 미결 사항 (사용자 확인 필요)

- FAQ 99의 본문: 결정표에서 "본문 보완"을 고르면 본문을 받아야 한다.
- 근접 중복 FAQ 5와 250: 병합하지 않고 대체 정답으로 뒀다. 사용자가 결정표에서 바꾸면 병합표에 추가한다.
- 사전등록 경로가 FAQ마다 다르다(288 국가공무원채용시스템, 289 통합채용포털, 247 사이버국가고시센터). 원본의 상충이므로 고치지 않는다. 생성 평가에서 세 경로를 모두 정답으로 볼지 사용자에게 묻는다.

## 10. 작업이 끝나면 보고할 것

사용자는 결과를 claude.ai의 경력 정리 문서에 옮긴다. 아래를 한 번에 정리해 준다.

- `faq-v2` 행 수와 변경 내역
- 평가셋 v1.2의 문항 수, 유형 분포, 작성자 분포, 대체 정답이 있는 문항 수
- `CHANGES.csv`의 건수(필드별)
- 커밋 해시와 태그
- 재실험을 했다면 구성별 Hit@1, Hit@3, Group Recall@3, MRR(단일), 범위 밖 차단 건수, 문항 수
