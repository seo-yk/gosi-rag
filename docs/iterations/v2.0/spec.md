# gosi-rag 2차 이터레이션 기능 명세

상태: 초안  
대상: 단일 턴 국가공무원 채용시험 FAQ RAG  
근거 문서: [design.md](design.md)

## 1. 목적과 범위

이 명세는 입력 검증부터 검색, 답변 생성, 기록, 오프라인 평가까지 2차 이터레이션에서 구현할 동작과 수용 기준을 정의한다.

범위에 포함한다.

- 텍스트 입력의 사전 검증과 정규화
- 검색 유사도 필터와 입력 예산에 따른 컨텍스트 조합
- 프롬프트 구성과 LLM 호출의 분리
- API 규격별 LLM 어댑터와 제한된 대체 호출
- 출력 정제와 오류 분류
- 단계별 구조화 로그와 생성 기록
- 데이터셋·인덱스 버전 관리
- 생성과 분리된 LLM-as-a-Judge 평가

범위에서 제외한다.

- 멀티턴 대화와 대화 메모리
- 실시간 Judge 호출
- 문서 자동 요약·재정렬·청크 내부 절단
- 동적 프롬프트 편집과 대체 템플릿
- 별도 관측·스냅샷 저장 서비스
- 비텍스트 URL의 원격 MIME 검사

## 2. 공통 규칙

- `MUST`는 이번 이터레이션의 필수 요구사항이다.
- `SHOULD`는 특별한 사유가 없다면 적용해야 한다.
- 설정값의 구체 수치는 구현 설정에서 관리한다. 이 명세는 수치를 임의로 확정하지 않는다.
- 처리 단계가 거부·유보·실패로 종료되면 명시적으로 허용된 복구 외의 후속 단계를 실행하지 않아야 한다.
- 사용자 메시지에는 내부 예외, API 키, 공급자 응답 원문 등 민감하거나 불필요한 진단 정보를 포함하지 않아야 한다.

## 3. 입력 처리

### INP-001 텍스트 입력만 허용

시스템은 입력 정규화 전에 입력 형식을 검사해야 한다.

수용 기준:

- 문자열 입력은 다음 검사를 진행한다.
- bytes, 파일, 이미지 등 비문자열 입력은 거부한다.
- 거부 후 정규화·임베딩·검색·LLM 호출 횟수는 모두 0이다.
- 거부 사유를 `input_validation` 로그에 기록한다.

### INP-002 길이 초과 입력 차단

시스템은 설정된 문자 길이 상한을 초과한 원문을 정규화 전에 거부해야 한다.

수용 기준:

- 길이가 상한과 같으면 다음 검사를 진행한다.
- 길이가 상한보다 크면 자동 절단 없이 거부한다.
- 거부 후 정규화·임베딩·검색·LLM 호출 횟수는 모두 0이다.
- 사용자에게 허용 길이 이내의 질문을 요청한다.

### INP-003 비텍스트 URL 차단

시스템은 로컬 규칙으로 식별 가능한 이미지·오디오·영상 URL과 비텍스트 data URI를 거부해야 한다.

수용 기준:

- 일반 웹페이지 URL이 포함된 텍스트 질문은 허용한다.
- 지원하지 않는 미디어 확장자 또는 비텍스트 data URI가 포함되면 거부한다.
- URL 판별을 위해 외부 네트워크를 호출하지 않는다.
- 확장자가 없거나 리다이렉트되는 URL의 실제 유형까지 판별한다고 보장하지 않는다.

### INP-004 텍스트 정규화와 UTF-8 처리

사전 검증을 통과한 문자열은 NFC, 줄바꿈, 앞뒤 공백을 정규화하고 UTF-8 strict 인코딩 가능 여부를 검사해야 한다.

수용 기준:

- 조합 방식이 다른 동등한 한글은 NFC 결과가 같다.
- CRLF와 CR 줄바꿈은 LF로 통일한다.
- 앞뒤 공백은 제거하되 본문 내부의 의미 있는 공백은 보존한다.
- UTF-8로 표현할 수 없는 입력은 문자를 삭제·대체하지 않고 인코딩 오류로 종료한다.
- 정규화 후 빈 문자열 또는 길이 초과 입력은 임베딩으로 전달하지 않는다.

## 4. 검색과 컨텍스트 조합

### RET-001 검색 결과 메타데이터

검색기는 Top K 청크와 각 청크의 식별자·원본 출처·검색 순위·유사도 점수를 반환해야 한다.

수용 기준:

- 각 결과에 문자열 `chunk_id`, 문자열 `source_document_id`, 1부터 시작하는 `retrieval_rank`, `similarity_score`가 있다.
- 회수된 청크 수와 설정된 Top K를 기록한다.
- 같은 FAQ에서 나온 여러 청크를 `chunk_id`로 구분할 수 있다.

### RET-002 유사도 임곗값 적용

시스템은 검색 결과에 현재 `index_version`에 연결된 유사도 임곗값을 적용해야 한다.

수용 기준:

- 점수가 임곗값 이상인 청크만 통과한다.
- 검색 결과가 없는 상태와 결과가 모두 임곗값 미달인 상태를 구분한다.
- 통과 청크가 없으면 안전 응답을 반환하고 프롬프트 구성·LLM 호출을 실행하지 않는다.
- 유보는 시스템 오류가 아닌 정상 상태로 기록한다.
- 임곗값, 임곗값 버전, 최고 점수, 통과 청크 수와 결정을 기록한다.

### RET-003 임곗값 측정 모드

검증되지 않은 임곗값은 차단에 사용하기 전에 측정 모드로 평가해야 한다.

수용 기준:

- 측정 모드에서는 예상 결정과 실제 결정을 별도로 기록한다.
- 답변 가능 질문의 오거부율과 범위 밖 질문의 차단율을 산출할 수 있다.
- 임베딩 모델·청킹·임베딩 필드 등 검색 설정이 바뀌면 임곗값을 다시 검증한다.

### CTX-001 입력 예산 적용

시스템은 시스템 지시·질문·역할 포장·검색 근거와 예약 출력량을 고려해 모델 입력 예산을 적용해야 한다.

수용 기준:

- 모델의 컨텍스트 한도에서 출력 상한을 먼저 예약한다.
- 예산을 초과하면 검색 순위가 낮은 청크부터 청크 전체를 제외한다.
- 시스템 지시와 사용자 질문은 자르지 않는다.
- 청크 내부 절단·자동 요약·재정렬은 수행하지 않는다.
- 하나의 근거 청크도 담을 수 없으면 생성하지 않고 입력 예산 부족 상태로 종료한다.
- 정확한 토큰 계산을 사용할 수 없으면 추정 방식과 안전 여유를 기록한다.

### CTX-002 최종 컨텍스트 기록

시스템은 임곗값 통과 청크와 실제 모델에 전달한 청크를 구분해야 한다.

수용 기준:

- 각 청크에 `retrieval_rank`, `context_position`, 포함 여부와 제외 사유를 기록한다.
- 실제 전달 청크는 검색 순서를 유지한다.
- 최종 FAQ 라벨·제목·본문·순서를 포함한 컨텍스트 본문을 생성 기록에 저장한다.
- Judge는 필터 전 검색 결과나 최신 원문이 아니라 해당 생성 기록의 최종 컨텍스트를 사용한다.

## 5. 프롬프트 구성

### PRM-001 프롬프트 요소 분리

프롬프트 구성기는 시스템 지시, 최종 FAQ 컨텍스트, 사용자 질문을 구분해 조합해야 한다.

수용 기준:

- 시스템 지시에는 역할, FAQ 근거 제한, 추측 금지, 출력 규칙이 포함된다.
- 검색 문서와 사용자 질문을 시스템 지시로 취급하지 않는다.
- 별도 배경과 few-shot 예시는 포함하지 않는다.
- 외부 데이터 검색과 LLM 호출을 수행하지 않는다.
- 템플릿 버전을 결과와 로그에 기록한다.

### PRM-002 필수 요소 누락 처리

프롬프트 구성기는 질문·시스템 지시·최종 컨텍스트가 누락되거나 렌더링에 실패하면 중단해야 한다.

수용 기준:

- 구성 실패는 검색 결과 없음과 다른 오류로 분류한다.
- 사용자에게 답변 준비 중 오류가 발생했다는 메시지를 반환한다.
- 대체 템플릿을 사용하지 않는다.
- LLM 호출 횟수는 0이다.

## 6. LLM 호출

### LLM-001 공통 호출 계약

공통 호출기는 공급자와 관계없이 같은 요청·응답 계약을 제공해야 한다.

수용 기준:

- 요청은 프롬프트, 모델 설정, timeout, 출력 상한을 포함한다.
- 성공 응답은 텍스트, 공급자, 모델, 종료 사유, 공급자 요청 ID와 사용량을 가능한 범위에서 반환한다.
- 제공되지 않은 사용량은 0이 아닌 null로 기록한다.
- 공급자별 응답 구조가 출력 처리기로 노출되지 않는다.

### LLM-002 API 규격별 어댑터

시스템은 Gemini와 OpenAI 호환 API를 별도 어댑터로 지원해야 한다.

수용 기준:

- 같은 API 규격의 모델 교체는 모델 설정 변경으로 가능하다.
- 새로운 요청·응답 규격은 기존 출력 처리기를 수정하지 않고 어댑터를 추가해 지원할 수 있다.
- 어댑터는 프롬프트 구획의 의미와 최종 컨텍스트 순서를 변경하지 않는다.
- SDK 자동 재시도는 비활성화한다.

### LLM-003 제한된 대체 호출

기본 Gemini 호출의 일시적 서버 오류 또는 속도 제한에 한해 설정된 경우 OpenAI 대체 호출을 한 번 허용한다.

수용 기준:

- 정상 답변은 모델 호출 1회로 끝난다.
- 허용된 실패 시 전체 모델 호출은 최대 2회다.
- 대체 호출은 별도 `generation_id`를 사용하고 같은 `request_id`에 연결한다.
- 인증 오류·잘못된 요청·지원하지 않는 옵션·타임아웃에는 대체 호출하지 않는다.
- 대체 호출도 실패하면 추가 호출 없이 종료한다.

### LLM-004 시간 예산과 타임아웃

시스템은 요청 전체 deadline과 호출별 timeout을 적용해야 한다.

수용 기준:

- 호출 timeout은 모델별 설정과 남은 전체 시간 중 작은 값을 사용한다.
- 대체 호출 최소 잔여 시간보다 적게 남으면 대체 호출하지 않는다.
- 타임아웃은 호출기 내부에서 종료하고 출력 처리를 실행하지 않는다.
- 타임아웃을 포함한 모든 종료 경로에서 요청 종료 로그를 한 번 남긴다.

## 7. 출력과 오류 처리

### OUT-001 일반 텍스트 출력 처리

사용자 답변은 일반 텍스트로 처리해야 한다.

수용 기준:

- 앞뒤 공백과 줄바꿈을 정규화한다.
- 명확히 정의된 상투적 서두만 제거한다.
- 목록·본문·인라인 코드·정당한 답변 유보 문장은 보존한다.
- 빈 결과는 출력 오류로 반환한다.
- 출력 처리기는 LLM을 호출하지 않는다.

### OUT-002 평가 JSON 처리

평가 응답은 JSON으로 파싱하고 스키마를 검증해야 한다.

수용 기준:

- 전체 응답을 감싼 명확한 코드 펜스는 제거할 수 있다.
- JSON 문자열 내부의 Markdown·백틱은 변경하지 않는다.
- 모호한 여러 JSON 후보 중 하나를 임의 선택하지 않는다.
- 파싱 실패와 스키마 불일치를 서로 다른 오류로 반환한다.
- 실패한 원시 텍스트를 정상 평가 결과로 반환하지 않는다.

### OUT-003 에이전트용 응답 계약

시스템은 파이프라인 결과를 애플리케이션이 조립한 구조화 응답으로 반환해야 한다.

수용 기준:

- 최상위 상태는 `answered`, `abstained`, `rejected`, `failed` 중 하나다.
- 세부 원인은 단일 `reason_code`와 종료 `stage`로 표현한다.
- 검증 실패는 첫 실패에서 즉시 반환하며 복합 오류 배열을 만들지 않는다.
- 모델이 생성한 상태값을 신뢰하지 않고 애플리케이션이 실제 실행 결과로 상태를 결정한다.
- 검색된 출처, 모델에 전달된 출처, 답변이 인용한 출처를 구분한다.
- 실제 LLM 호출이 두 번 이상 수행된 복구 흐름에만 `attempts` 배열을 포함한다.
- 사용자 응답에는 내부 예외와 공급자 원문 오류를 포함하지 않는다.

### ERR-001 오류 정책 결정

오류 정책은 오류 유형과 호출 이력·남은 시간에 따라 중단 또는 대체 호출을 결정해야 한다.

수용 기준:

- 정책 함수는 SDK·UI·저장소를 직접 호출하지 않는다.
- 정책 결과는 `stop` 또는 `use_fallback`과 사용자 메시지를 포함한다.
- 실행 조율자가 결정을 적용하고 공통 호출기가 호출 한도를 최종 검사한다.
- 출력 파싱·검증 실패에는 자동 재생성을 허용하지 않는다.

## 8. 관측과 기록

### OBS-001 식별자

시스템은 요청·생성·평가를 서로 다른 식별자로 연결해야 한다.

수용 기준:

- 질문 처리마다 새로운 `request_id`를 만든다.
- 실제 모델 호출마다 새로운 `generation_id`를 만든다.
- 특정 생성 결과의 평가마다 새로운 `evaluation_id`를 만든다.
- 모델 호출 전 종료된 요청의 `generation_id`는 null이다.
- `question_id`는 평가 데이터셋 식별자로만 사용한다.

### OBS-002 단계별 구조화 로그

시스템은 JSON Lines 형식으로 단계별 로그를 남겨야 한다.

수용 기준:

- 공통 필드는 시각, request_id, 단계, 이벤트, 상태, 소요 시간, 오류 유형이다.
- 입력 수신이 첫 로그이며 제한된 입력 미리보기와 길이를 포함한다.
- 검색 로그에는 청크·출처·순위·유사도와 개수를 포함한다.
- 모델 호출 로그에는 generation_id, 모델, 시도 순서, 대체 사유, timeout, 사용량을 포함한다.
- 종료 로그에는 최종 상태와 실패 단계를 포함한다.
- API 키와 전체 본문을 운영 로그에 반복 저장하지 않는다.
- 로그 기록 실패가 LLM 재호출의 원인이 되지 않는다.

### REC-001 생성 원본 기록

생성 결과는 JSONL 원본 기록으로 저장해야 한다.

수용 기준:

- 기록에는 schema_version, 식별자, 데이터·인덱스·프롬프트·모델 버전, 질문, 검색 결과, 통과 청크, 최종 컨텍스트, 답변과 실행 상태가 포함된다.
- 검색 출처, 실제 전달 출처, 명시적 인용을 구분한다.
- 검색 결과 밖과 실제 전달 목록 밖의 인용을 식별할 수 있다.
- 일반 텍스트 답변에서 모델 자기보고 상태를 추측하지 않고 null로 기록한다.
- CSV는 분석용 내보내기 형식이며 JSONL을 대체하지 않는다.

### REC-002 인용 처리

현재 FAQ 답변의 명시적 인용은 `[FAQ N]` 형식으로 처리해야 한다.

수용 기준:

- 내부 source_document_id는 문자열로 취급한다.
- 화면 라벨과 내부 식별자를 매핑한다.
- 중복 인용을 제거하되 답변 원문을 변경하지 않는다.
- 명시적 인용이 없다는 이유만으로 근거성 실패로 판정하지 않는다.

## 9. 데이터와 인덱스 버전

### VER-001 데이터셋 버전

FAQ 추가·수정·삭제가 발생하면 새로운 `dataset_version`을 만들어야 한다.

수용 기준:

- 버전에는 원본 데이터, 제공 기관, 출처 URL, 내용 해시가 연결된다.
- 기존 버전의 원본과 manifest를 덮어쓰지 않는다.
- 생성·평가 기록에서 사용한 dataset_version을 참조한다.
- 원문 수정일·시행일이 제공되면 보존한다.

### VER-002 인덱스 버전

데이터셋 또는 검색 설정이 변경되면 새로운 `index_version`을 만들어야 한다.

수용 기준:

- 버전에는 dataset_version, 임베딩 모델과 가능한 경우 리비전, 청킹 방식, 임베딩 필드, FAISS 파일·청크 메타데이터의 해시가 포함된다.
- 인덱스와 메타데이터의 버전이 일치하지 않으면 로드를 거부한다.
- 임곗값은 검증된 index_version에 연결한다.
- 생성·평가 기록에서 사용한 index_version을 참조한다.

### VER-003 기록 스키마 버전

JSONL 기록 구조는 dataset_version·index_version과 별도인 `schema_version`으로 관리해야 한다.

수용 기준:

- 호환되지 않는 구조 변경 시 schema_version을 변경한다.
- 기존 CSV를 덮어쓰거나 불명확한 과거 기록을 자동 연결·재분류하지 않는다.

## 10. 오프라인 평가

### EVAL-001 생성과 평가 분리

LLM-as-a-Judge는 실시간 답변 경로와 별도로 실행해야 한다.

수용 기준:

- Judge 호출은 사용자 응답 지연과 실시간 생성 비용에 포함되지 않는다.
- Judge는 평가 대상 generation_id의 질문·답변·최종 전달 컨텍스트를 사용한다.
- 필터 전 전체 검색 결과나 현재 원문으로 조용히 대체하지 않는다.

### EVAL-002 평가 실행 상태와 품질 판정 분리

평가 실행 성공 여부와 답변 품질 판정은 별도 필드로 저장해야 한다.

수용 기준:

- 성공한 평가는 `evaluation_status=succeeded`와 품질 판정을 저장한다.
- API·입력 기록·파싱·스키마 오류는 `evaluation_status=failed`로 저장한다.
- 평가 실패 시 overall·근거성·정확성 등 품질 필드는 null이다.
- 평가 기록이 없는 생성 결과는 미평가 상태로 계산한다.
- 품질 통계는 성공한 평가만 분모에 포함하며 실패·미평가 수를 별도로 보고한다.

## 11. 완료 조건

2차 이터레이션은 다음 조건을 모두 만족할 때 완료로 본다.

- 모든 MUST 요구사항에 대응하는 자동화 테스트가 있다.
- 요구사항 ID와 구현 파일·테스트 파일의 연결표가 작성되어 있다.
- 실제 외부 API 없이 입력 거부, 검색 유보, 기본 호출 성공, 대체 호출, 타임아웃, 출력 실패를 검증할 수 있다.
- 전체 기존 테스트와 신규 테스트가 통과한다.
- 생성 원본 기록으로 당시 질문·검색 결과·최종 컨텍스트·모델 호출·답변을 재현할 수 있다.
- 평가기 실패가 답변 품질 실패로 집계되지 않는다.
- 데이터셋·인덱스 버전 불일치를 차단할 수 있다.
