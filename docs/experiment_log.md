## 1. 출발점: 1차 실험을 다시 쓰지 않는 이유

1차 결과(검색 Hit@1 90.2%, 사람·자동 채점 일치율 91.67%)는 근거로 다시 쓰지 않기로 했다.

1. **원본 FAQ의 제목과 본문이 어긋나 있었다.** 연번 100~200(101건)의 본문이 한 칸씩 밀려 각 행에 다음 질문의 답이 들어 있었다. 1차 최종 조합은 제목만 임베딩해서 검색 영향은 작았을 수 있지만, 본문을 쓰는 조합과 생성 단계는 직접 영향을 받았다.
2. **모델마다 평가 문항 수가 달랐다**(e5 51문항, OpenAI 50문항).
3. **검색용(50)과 생성용(60) 평가셋이 따로 있었다.**
4. (재실험 중 추가 발견) **Top-3로 검색한 결과로 Hit@5를 계산**해서 Hit@3과 Hit@5가 항상 같았다.
5. (재실험 중 추가 발견) `paragraph` 청킹은 본문에 빈 줄이 없어 `row`와 같았고, `file` 청킹은 청크가 1개라 비교가 성립하지 않았다. 사실상 청킹 비교가 없었다.

1차 파일은 지우지 않고 `archive/experiment-v1/`로 옮겼고, 당시 저장소 상태는 태그 `experiment-v1`로 고정했다.

- **단일 평가셋:** 150문항 중 의도가 같은 2문항(12, 130)을 제외한 148문항. 범위 밖 질문 10문항은 별도 묶음이다.

  - 기각 사례: 44번은 대체 정답 제안을 기각하고 원래 라벨을 유지했다.
  - 오류 수정: 122번 보조 FAQ를 262에서 261로 바로잡았다(메모 내용과 FAQ 번호 불일치).
- **동결:** 태그 `evalset-v1.2`. 이후 라벨을 바꾸려면 버전을 올린다.

### 3-2. v1.3: 형식 정리

- ID를 `q001`에서 `1`로 바꿨다(원본 FAQ 연번과 같은 형식). 범위 밖은 `154~163`으로 이어 붙여 번호가 겹치지 않게 했다.
- 칼럼을 15개에서 10개로 줄였다. 다른 칼럼으로 계산되는 것(`evidence_type`), 채점에 쓰이지 않는 것(`multi_intent`), 값이 늘 같은 것(`expected_behavior`, `label_author`, `eval_set_version`, 범위 밖의 `pass_rule`)을 뺐다. 범위 밖 판정 규칙은 README 채점 규칙으로 옮겼다.
- 라벨과 문구는 v1.2와 같다. 태그는 `evalset-v1.3`이다.
- FAQ 칼럼 이름(`제목/본문`)과 평가셋 칼럼 이름(`question/reference_answer`)은 맞추지 않았다. 둘은 역할이 다르고(문서 대 질의·정답), FAQ 칼럼 이름은 임베딩 입력과 생성 프롬프트에 그대로 들어가 바꾸면 실험 조건이 달라진다.

## 4. 검색 평가 설계 (`docs/1_retrieval.md`)

### 4-1. 지표

| 지표 | 정의 | 왜 |
|---|---|---|
| Hit@K | 모든 필수 그룹이 Top-K에서 충족되면 1 | 복수 근거 질문은 근거가 다 있어야 답할 수 있다 |
| Group Recall@K | 충족 그룹 수 ÷ 전체 그룹 수 | 부분 충족을 구분해서 본다 |
| MRR | 단일 그룹 문항(111)만 | 복수 그룹에서는 "가장 높은 순위"가 정의되지 않는다 |
| 범위 밖 | Top-1 유사도와 Top-5만 기록, 임곗값 없음 | 지표 대신 측정만 한다 |

- **Hit@1의 구조적 한계 발견:** 복수근거 37문항은 Top-1에 FAQ가 하나뿐이라 Hit@1이 항상 0이다. 그래서 전체 Hit@1의 최댓값은 75.0%다. 1차 수치(90.2%)와 나란히 놓으면 성능이 떨어진 것처럼 보이므로, **단일 그룹 111문항 기준 Hit@1을 따로 보고**한다.
- **한 번 검색해서 @1·@3·@5 계산:** 1차의 Hit@3 = Hit@5 문제를 없앴다. 검색 쪽 Top-K 비교도 불필요해졌다.
- **유형별·작성자별 묶음**을 함께 낸다(편향 점검용).

### 4-2. 청킹

- **title/body 구분은 청킹이 아니다.** 청킹은 문서를 자르는 단위이고, `title`/`title_body`는 청크를 어떤 텍스트로 벡터화할지(임베딩 입력)의 문제다. 문서에서도 둘을 다른 축으로 구분했다.
- **문장 단위 청킹(`sentence`) 추가:** 1차 해석의 "세부 키워드가 본문에만 있어 회수되지 않았다"를 검증하려는 가설이다. 문장마다 FAQ 제목을 머리말로 붙여 문맥을 유지했다. 날짜("2007.12.31.") 안에서 자르지 않도록 한글·괄호 뒤 마침표에서만 자른다. 20자 미만 조각은 앞 문장에 붙인다. 결과는 634청크(FAQ당 2.2개)다.
- `sentence × title` 조합은 만들지 않았다. 청크마다 제목이 같아 같은 벡터가 반복되기 때문이다.
- **FAQ 기준 중복 제거:** 같은 FAQ의 문장들이 Top-5를 채우면 순위가 왜곡된다. 청크 50개를 검색한 뒤 FAQ 번호로 중복을 지우고, 서로 다른 FAQ 5개로 채점한다.

### 4-3. 임베딩 모델 선정 (12조합)

| 모델 | 역할 | 선정 이유 |
|---|---|---|
| multilingual-e5-small | 기준선 | 1차 최고 모델 |
| BAAI/bge-m3 | 다국어 대형 | KURE의 바탕 모델. 한국어 추가 학습 효과를 분리하는 대조군 |
| nlpai-lab/KURE-v1 | 한국어 특화 | 데이터가 전부 한국어 |
| text-embedding-3-large | 상용 API | 상용 비교. 같은 계열의 3-small은 정보가 적어 제외 |

- 접두어 공정성: e5만 `query:`/`passage:`를 붙인다. 그 모델의 학습 형식이기 때문이다. 모든 모델에 붙이거나 모두 빼면 오히려 일부 모델이 손해를 본다. 데이터, 질문, 청킹, 검색 방식, 채점은 모두 같다. 접두어 없는 e5 대조 실험은 하지 않기로 했다.

### 4-4. 무결성 장치 (검토 중 발견해 추가)

| 발견 | 위험 | 조치 |
|---|---|---|
| e5 접두어가 모든 로컬 모델에 붙고 있었음 | bge-m3·KURE가 부당하게 낮게 나옴 | e5 계열에만 적용 |
| 인덱스와 질문의 모델이 달라도 오류 없음 | 차원이 같은 모델(bge-m3·KURE 1024차원)끼리는 결과가 조용히 틀림 | 인덱스마다 `manifest.json`(원천 CSV 해시, 모델)을 남기고 대조. 평가와 앱 모두 |
| 정답 FAQ가 인덱스에 없어도 오답으로만 처리 | 데이터 문제를 성능 저하로 착각 | 정답 FAQ 누락 시 중단 |
| 조합마다 질문을 다시 임베딩 | 질문 쪽 조건이 미세하게 달라지고 API 호출도 늘어남 | 모델별 질문 벡터 캐시(OpenAI 호출 474→158회) |
| 인덱스 폴더가 모델과 무관하게 하나 | 모델 간 인덱스가 섞이거나 앱이 다른 인덱스를 읽음 | 폴더를 `index/faq_v2/<모델 이름>`으로 자동 결정 |
| 인덱스 생성 기본값이 OpenAI·로컬을 함께 쓰면서 모델 이름은 하나만 받음 | README대로 실행하면 실패 | 제공자 하나만 쓰도록 변경 |

## 5. 평가셋 편향 점검

질문과 정답 FAQ 제목의 글자 2-gram 겹침을 측정했다.

| 묶음 | 겹침 평균 |
|---|---|
| Claude 초안(91문항) | 0.53 |
| 본인 작성(57문항) | 0.34 |
| 원문유사 / 조건형 / 일상표현 / 복수근거 | 0.63 / 0.53 / 0.40 / 0.29 |

- 검색 결과에서도 모든 조합에서 Claude 초안 문항의 Hit@3이 3.9~11.2%p 높았다.
- **원인 분석:** 단일 그룹 유형은 작성자와 관계없이 Hit@3이 100%였고, 차이는 전부 복수근거 문항에서 나왔다(본인 5/10, Claude 24/27).
  - 본인의 복수근거 질문 10개 중 9개는 원래 정답이 1개인 질문이었는데, 라벨 검토에서 필수 근거가 추가됐다. 질문을 먼저 쓰고 근거를 나중에 찾은 셈이라, 필요한 근거 일부가 질문에 드러나지 않는다.
  - Claude 초안은 FAQ 두 개를 먼저 고르고(27개 중 22개가 이웃 번호) 각 FAQ에 대응하는 절을 붙였다.
  - 결론: 원인은 Claude의 문체가 아니라 **"FAQ를 보고 질문을 만든" 작성 방식**이다. 실제 사용자 질문에 가까운 난이도는 본인 작성 복수근거 문항이 보여 준다(10문항이라 확정적이지 않음).
- 대응: 결과를 작성자별로 함께 보고한다. 개선 후보로 복수 질문을 하위 질문으로 나눠 검색하는 방식을 남겼다.

## 6. 검색 실험 결과 (`results/retrieval_v1.3/`)

Hit@1(단일 그룹 111문항 기준):

| 모델 | row × title | row × title_body | sentence × title_body |
|---|---:|---:|---:|
| e5-small | 90.1% | 91.9% | 91.0% |
| bge-m3 | 91.9% | 97.3% | **98.2%** |
| KURE-v1 | 94.6% | 95.5% | 97.3% |
| text-embedding-3-large | 91.0% | 92.8% | 94.6% |

1. 5%p를 넘는 모델 차이는 bge-m3와 e5-small 사이(+5.4%p) 하나뿐이다. 한국어 특화(KURE)나 유료 API(3-large)가 무료 다국어 대형 모델보다 낫다는 근거는 없었다.
2. 4개 모델 모두 `title_body`가 `title`보다 높다(+0.9~+5.4%p). 1차 결론("제목만이 낫다")은 재현되지 않았다. 본문 교정의 효과일 가능성이 있다.
3. 문장 청킹과 `row`는 차이가 확인되지 않았다. FAQ가 짧아(평균 255자) FAQ 하나를 그대로 청크로 둬도 충분했다.
4. e5-small은 범위 밖 질문도 유사도 0.85 안팎이라 임곗값으로 걸러내기 어렵다.

**생성 단계 구성:** bge-m3 + `row` + `title_body` + Top-3. 상위권이고 무료이며, FAQ 단위 근거라 추가 구현이 필요 없다. `sentence`(수치상 최고)는 차이가 확인되지 않았고, 생성에 쓰려면 원래 FAQ 전체를 근거로 넘기는 처리가 추가로 필요하다.

## 7. 생성 실험 설계 (`results/generation_v1.3/`)

| 조건 | 생성 모델 | 근거 | 답하려는 질문 |
|---|---|---|---|
| A | gpt-5.4-mini | 검색 Top-3 | 지금 파이프라인 전체의 답변 품질 |
| B | gpt-5.4-mini | **정답 FAQ(오라클)** | 답변 품질의 상한. A와의 차이로 "검색 탓 대 생성 탓"을 분리 |
| C | EXAONE 3.5 7.8B(로컬) | 검색 Top-3 | 유료 API 대신 무료 한국어 특화 로컬 모델로 충분한가 |

**하지 않은 것과 이유**
- 생성 모델을 여러 개로 늘리지 않음: 비교 축을 "API 대 로컬" 하나로 좁혀 채점 부담과 해석을 단순하게.
- `gemma3:4b`를 생성에 쓰지 않음: 채점 모델과 같아서 자기 답변을 후하게 볼 위험.
- `qwen2.5:3b` 대신 EXAONE: 3B는 "작아서 졌다"로 끝나기 쉽다. 한국어 특화 로컬 모델이 검색 실험의 KURE 비교와 이어진다.
- 생성 Top-K 3과 5 비교 안 함: 검색 Hit@3과 Hit@5 차이가 작아 변별력이 낮고, 1차에서도 차이가 없었다.

**구현**
- 오라클 모드: 필수 그룹의 FAQ 전부(대체 정답 포함)를 근거로 넣는다. 근거 수는 문항마다 1~4개로, A의 3개와 다르다(상한 측정이 목적이라 의도된 차이).
- 문항마다 바로 저장하고, 실패하면 이어서 실행한다. 비용이 드는 호출을 다시 하지 않기 위해서다.
- 생성 결과 칼럼은 평가셋과 같은 이름 규칙의 10개다(`id`, `type`, `question`, `required_faqs`, `reference_answer`, `model`, `context_setup`, `context_faqs`, `context_text`, `answer`).
- 범위 밖 10문항은 A와 C에서 생성하고, 자동 채점에서 빼 사람이 판정한다.

**실행 기록:** A 158회·B 148회 OpenAI 호출(각 수 분). C는 로컬에서 158문항에 약 5시간 걸렸다(문항당 약 2분). 답변 길이 평균은 A 258자, B 235자, C 366자다.

## 8. 생성·채점 파이프라인 점검

### 8-1. Ollama 컨텍스트 잘림 (가장 중요한 발견)

- **현상:** 모델에 `num_ctx`가 없으면 Ollama 서버는 컨텍스트를 2,048토큰으로 잡는다. 이를 넘는 프롬프트는 **앞부분(규칙·질문·기준 답변)이 경고 없이 잘린다.** 모델이 원래 처리할 수 있는 길이는 32K~128K다.
- **확인 방법:** 맨 앞에 표식을 넣은 긴 입력으로 실험했다. 2,048토큰을 넘자 `prompt_tokens=2051`에서 멈췄고 표식을 기억하지 못했다.
- **영향 측정:**

  | 대상 | 2,048토큰을 넘은 채점 프롬프트 |
  |---|---|
  | 1차 채점 | 60개 중 1개(최대 2,319) → 1차 채점 결과에 미친 영향은 작음 |
  | A | 148개 중 2개 |
  | B | 0개 |

- **조치:** `num_ctx 8192` 모델을 만들고 설정 파일(`evaluation/ollama/*.Modelfile`)을 저장소에 남겼다. Ollama 호출마다 입력 토큰이 한도에 닿으면 중단하도록 했다(생성·채점 공통). 7,000토큰 입력도 앞부분까지 읽는 것을 확인했다.

### 8-2. 채점 파싱 실패

- 이전에는 채점 결과(JSON)를 읽지 못하면 그 답변을 "불합격"으로 셌다. 채점기 오류가 답변 품질로 잘못 집계되는 구조였다.
- 이제 2번 다시 요청하고, 그래도 실패하면 `error`로 따로 센다.

### 8-3. 루브릭 v1 → v2

v1(1차): 근거성 0~2, 정확성 0/1, 완결성 0/1. 합격은 근거성 1 이상이면서 정확성·완결성 1.

| v1의 약점 | v2의 대응 |
|---|---|
| 근거성 1("일부만 근거")도 합격 → 환각이 섞여도 통과 | 근거성 2만 합격 |
| 완결성 기준이 모호 → 복수 질문에서 일부만 답해도 통과 | 평가셋의 필수 근거 그룹별로 판단(`groups_covered`) |
| 근거가 있는데 답을 피한 경우의 규칙 없음(1차 불일치의 주된 원인) | `unjustified_refusal` 항목 |
| 길이·서식 편향에 무방비 | 길이·서식·말투를 무시하라고 명시 |
| 표현이 다르거나 대체 근거로 맞힌 답을 오답 처리할 수 있음 | 같은 뜻의 다른 표현 인정, 근거 FAQ끼리 다르면 하나에 근거한 답 인정 |
| 점수만 받음 → 사람이 판단 근거를 볼 수 없음 | 판단 근거(`reason`)를 먼저 쓰게 함 |
| 채점기 검증이 60문항뿐이고, 잘림 가능성도 있었음 | 블라인드 사람 채점으로 재검증 |

- **v2 → v2.1 (2026-11-13, 사람 채점 중 발견):** v2에는 "회피면 정확성 0" 규칙이 있었다. 이 규칙은 질문 전체를 피한 경우만 생각한 것이었다. 사람 채점 중 "두 가지를 물었는데 하나는 맞게 답하고 다른 하나는 근거가 있는데 피한" 답변에서 맞게 답한 부분까지 정확성 0이 되는 문제가 드러났다. 같은 결함이 정확성·그룹 충족·회피에서 이중으로 깎이는 셈이다. v2.1에서는 세 항목이 각각 하나만 보게 했다: 정확성 = 쓴 내용이 맞는가, 그룹 충족 = 빠뜨렸는가, 회피 = 근거가 있는데 일부라도 피했는가. 답을 준 뒤 덧붙인 안내("자세한 건 공고문 확인")는 회피가 아니라고 명시했다. 최종 판정 기준은 그대로라서 일부라도 피하면 여전히 불합격이다. 사람 채점과 채점 모델 프롬프트에 같은 규칙을 적용했다.
- 판정(`verdict`)은 채점 모델이 아니라 파이썬에서 점수로 계산한다(재현성).
- 1차 루브릭은 `evaluate_generation.py`에 그대로 두어 1차 결과를 재현할 수 있게 했다. 새 루브릭은 `judge_answers.py`다.

### 8-4. 소형 채점기의 한계 발견 → 채점 모델 선정 방식 변경

- 루브릭 v2로 4B 채점기(`gemma3-4b-ctx8k`)를 시험했다.
  - 형식 오류(따옴표 이스케이프, 그룹 수와 다른 배열)는 **JSON 스키마로 출력 형식을 강제**해 해결했다.
  - 판단 품질은 해결되지 않았다. FAQ에 그대로 있는 내용으로 맞게 답한 120번에 근거성 0·정확성 0을 줬고, 52번은 판단 근거에 "핵심을 잘 다뤘다"고 써 놓고 0·0을 줬다.
- 해석: 1차에서 일치율이 높았던 것은 루브릭이 느슨했기 때문일 수 있다. 촘촘한 루브릭에서는 소형 채점기의 한계가 드러난다.
- **결정:** 채점 모델을 미리 정하지 않는다. **블라인드 사람 채점 40문항을 먼저 하고, 후보 채점 모델들 중 사람과 가장 잘 맞는 모델을 채택**한다. 후보는 4B 로컬, 더 큰 로컬 모델, 다른 계열 API다. OpenAI 모델은 A·B와 같은 계열이라 자기 계열 답변을 후하게 볼 위험이 있어 주의한다.

### 8-5. 공정성 장치

| 위험 | 장치 |
|---|---|
| 채점기가 모델을 알아봄 | 채점 프롬프트에 모델 이름 없음 |
| 조건마다 다른 설정 | 같은 채점 모델·프롬프트, temperature 0 |
| 자기 선호 | 채점 모델(gemma)은 생성 모델(gpt, EXAONE)과 계열이 다름 |
| 사람 채점이 자동 점수에 끌림 | 사람 채점지에서 모델 이름·근거 구성·자동 점수를 숨기고 순서를 섞음. 조건 키는 채점이 끝날 때까지 열지 않음 |
| 길이 편향 | 답변 길이와 합격의 관계를 조건별로 보고. C의 답변이 가장 길어 C가 유리할 수 있음 |
| 채점 흔들림 | 일부 문항 반복 채점으로 일관성 확인 |
| 오라클(B)은 근거성이 쉽게 높음 | B는 상한 측정용. A·C와는 정확성·완결성 위주로 비교 |

**한계(기록):** B는 필수 근거와 제공 근거가 늘 같아서, 채점자가 두 칸을 비교하면 조건을 짐작할 수 있다. 채점에 근거가 필요해 숨길 수 없었다. 조건별 일치율로 그 영향을 확인한다.

### 8-6. 사람 채점지 설계 (`evaluation/human_review/`)

- 40문항: A 20 + B 20, 서로 다른 문항, 유형별 층화(조건마다 복수근거 6, 원문유사 4, 일상표현 5, 조건형 5), 시드 고정.
- 사전등록 경로가 FAQ마다 다른 문항(38, 49, 50, 55)을 일부러 넣었다. 원본끼리 상충하는 FAQ에서 채점이 흔들리는지 보려는 것이다.
- 입력: 근거성 0/1/2, 정확성 0/1, 그룹별 충족(예: `1|0`), 근거 있는데 회피 0/1, 메모. 채점하기 편하도록 Excel(열 너비·줄바꿈·선택 목록·채점 방법 시트)로 제공했다.
- **사람 채점의 독립성:** 채점이 끝난 파일을 Claude가 검토할 때는 형식만 확인했다(빈 칸, 허용되지 않는 값, 그룹 수 불일치, 규칙상 함께 나올 수 없는 조합, 행 순서). 판단 내용은 보지 않았다. LLM이 사람 판단을 고치게 하면 기준이 LLM 판단에 끌려가 "사람 대 채점기" 일치율이 의미를 잃기 때문이다. 불일치 사례를 나중에 다시 볼 경우에는 처음 채점과 다시 본 결과를 둘 다 남기고, 일치율은 처음 채점 기준으로 보고한다.
- **진행 기록:** 첫 제출본에서 형식 문제 8건이 나왔다(빈 칸 2행, "회피 1인데 정확성 1" 2행). 이 "회피·정확성" 충돌이 루브릭 v2.1(8-3)로 이어졌다. 고친 최종본은 형식 문제 0건이다. 사람 판정은 A 16/20 pass, B 19/20 pass, 전체 pass 35·fail 5였다. 결과는 `evaluation/human_review/1_ab_review/labels.csv`, 원본은 `evaluation/human_review/1_ab_review/sheet.xlsx`. 조건 키는 채점이 끝난 뒤에 공개했다.

### 8-7. 채점 모델 선정 과정과 결과 (`docs/3_judge_validation.md`)

후보마다 사람 채점 40문항을 같은 루브릭(v2.1)으로 채점하고, 사람과 비교했다. 사람 판정이 대부분 pass(35/40)라 무조건 pass라고만 해도 87.5%가 일치한다. 그래서 단순 일치율 대신 **Cohen's kappa(우연 일치 보정)와 사람 fail 검출**을 함께 봤다.

| 채점 모델 | 비교 문항 | 판정 일치 | kappa | 사람 fail 검출 | 사람 pass 유지 | 채점기 pass율 | 근거성 일치 | 그룹 충족 일치 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| gemma3-4b (로컬, 8K) | 40 | 40.0% | 0.10 | 5/5 | 11/35 | 27.5% | 52.5% | 50.9% |
| qwen2.5:7b (로컬, 8K) | 40 | 30.0% | 0.06 | 5/5 | 7/35 | 17.5% | 67.5% | 41.5% |
| gemini-2.5-flash | **24** | 91.7% | 0.70 | 3/4 | 19/20 | 83.3% | 83.3% | 90.3% |
| gemini-3.5-flash | 40 | 90.0% | 0.45 | 2/5 | 34/35 | 92.5% | 92.5% | 90.6% |
| gemini-3.7-flash | 40 | 90.0% | 0.45 | 2/5 | 34/35 | 92.5% | 90.0% | 90.6% |
| **gemini-3.8-flash (채택)** | 40 | 90.0% | 0.45 | 2/5 | 34/35 | 92.5% | 90.0% | 90.6% |

**과정**

1. **로컬 소형 모델 탈락:** 4B와 7B 모두 거의 모든 답을 fail로 줬다. 사람이 fail로 본 5문항을 다 잡은 것도 판단력 때문이 아니라 대부분을 fail로 줬기 때문이다. 시험 채점에서는 FAQ에 그대로 있는 내용으로 맞게 답한 답변(120번)에 근거성 0·정확성 0을 줬고, 판단 근거에 "핵심을 잘 다뤘다"고 써 놓고 0점을 준 경우(52번)도 있었다. 출력 형식 오류(따옴표 이스케이프, 그룹 수와 다른 배열)는 JSON 스키마로 출력 형식을 강제해 해결했지만, 판단 품질은 해결되지 않았다. 해석: 1차에서 4B 채점기의 일치율이 높았던 건 루브릭이 느슨했기(근거성 1도 합격) 때문일 수 있다.
2. **Gemini 무료 구간의 한계:** `gemini-2.5-flash`는 24문항에서 사람과 가장 잘 맞았다(kappa 0.70). 그러나 무료 구간 한도가 **프로젝트·모델당 하루 20회**였다. A 20문항을 채점하고 B를 4문항 채점한 시점에 한도에 걸렸다. 무료 한도 수치는 공개 자료(하루 1,500회 등)와 달랐고, 실제 값은 오류 메시지(`GenerateRequestsPerDayPerProjectPerModel-FreeTier`, 20)로 확인했다. 전체 채점(약 480회)을 무료로 하면 약 24일이 걸린다.
3. **키를 바꿔도 한도는 그대로:** 무료 한도는 키가 아니라 프로젝트·모델 단위다. 새 키로 시험한 결과, 새 키는 "신규 사용자"로 분류돼 `gemini-2.5-flash`와 `gemini-2.5-pro`가 아예 막혀 있었다(404, "no longer available to new users"). 그래서 2.5 Flash의 남은 16문항을 채울 수 없었고, 2.5 Flash 결과는 24문항으로 남았다. 한도를 피하려고 프로젝트를 나눠 쓰는 것은 이용 약관에 어긋날 수 있어 택하지 않았다.
4. **유료 전환:** Gemini 유료 구간은 선불 크레딧이고 최소 충전액은 10달러다. 실제 필요한 비용(1달러 안팎)보다 커서 OpenAI 모델을 채점기로 쓰는 안도 검토했다. 그러나 OpenAI 모델은 생성 모델(A·B의 gpt-5.4-mini)과 같은 계열이라 자기 계열 답변을 후하게 볼 위험이 있었다. 결국 10달러를 충전했다. 유료 구간은 보낸 데이터를 제품 개선에 쓰지 않는다는 점도 고려했다.
5. **Gemini 3.x Flash 비교:** 충전한 키에서 고정 버전 모델 3개(3.5·3.7·3.8 Flash)를 40문항으로 비교했다. 재현성을 위해 `-latest` 별칭과 미리보기 버전(`3.1-pro-preview`)은 쓰지 않았다. **세 모델의 판정이 같았고, 사람과 어긋난 문항도 같았다**(A-7, A-19, A-38, B-66). 채점기들끼리는 안정적이고, 사람과의 차이는 이 4문항에 몰려 있다.
6. **채택:** 세 모델의 결과가 같아서 가장 최신이고 이미 기본값으로 둔 `gemini-3.8-flash`를 채택했다. 사용량(40문항): 입력 약 5.3만 토큰, 출력 약 3.6천, 생각 토큰 약 1.2만.

### 8-11. 앱 화면 표시 개선

- 생성 답변에는 마크다운(굵게 A 142건·C 63건, 목록, 번호 목록)이 들어 있다. 앱은 원래 `st.write`로 이미 마크다운을 렌더링하고 있었다.
- 위험: Streamlit 마크다운은 `~` 두 개 사이를 취소선으로, `$`는 수식으로 해석한다. 이 데이터에는 범위 표기("3~4일", "8242~8251")가 많아, 한 답변에 두 번 나오면 핵심 정보에 취소선이 그어질 수 있다. 현재 답변·FAQ에는 한 텍스트에 `~`가 두 번 나온 경우가 없어 실제로 깨진 화면은 없었고, 예방 차원의 수정이다.
- 수정: 생성 답변은 마크다운을 유지하되 `~`·`$`만 문자 그대로 표시(`answer_markdown`). FAQ 원문과 제목은 일반 텍스트이므로 마크다운 특수문자를 모두 이스케이프해 원문 그대로 표시(`plain_text_markdown`). HTML은 Streamlit 기본값대로 해석하지 않는다. 테스트 4개를 추가했다.
- 앱 확인(2026-11-13): 새 구성(bge-m3 + row + title_body, 모델 대조 장치)으로 앱이 정상 동작했다. 실제 질문(기출문제·이의제기)에서 굵게 표시는 적용되고 "3~4일"은 그대로 보였으며, 출처 FAQ는 원문 그대로 표시됐다.

## 12. 포트폴리오에서 강조할 수 있는 점

- **데이터 품질 문제를 찾아 원인과 영향을 측정했다.** 원본 본문 밀림 101건과, 그것이 1차 결론("제목만 임베딩이 낫다")에 미쳤을 수 있는 영향.
- **평가 설계 자체를 검증했다.** Hit@1의 구조적 상한(75%), Top-3 검색으로 Hit@5를 계산하던 오류, 의미 없던 청킹 비교.
- **평가셋 편향을 측정하고 원인까지 분석했다.** 작성 방식에 따른 난이도 차이.
- **"조용히 틀리는" 실패를 장치로 막았다.** 인덱스와 질문 모델 불일치, Ollama 컨텍스트 잘림, 채점 파싱 실패를 오답으로 세던 문제.
- **비용 대비 성능 판단의 근거를 냈다.** 무료 다국어 대형 모델이 한국어 특화·유료 API와 차이가 확인되지 않았다.
- **원인 분리 실험을 설계했다.** 오라클 조건과 실패 원인 분해로, gpt-5.4-mini의 실패 10건 중 8건이 검색 누락이고 근거만 있으면 98%대로 답한다는 것을 보였다. 병목이 검색이라는 근거다.
- **사람의 유창성 편향을 실제로 확인했다.** 가독성 좋은 EXAONE 답변을 처음에는 사람이 통과시켰고, 근거와 대조한 뒤 7건 중 6건을 불합격으로 바꿨다.
- **LLM 채점기를 그대로 믿지 않았다.** 루브릭을 보강하고, 블라인드 사람 채점 40문항으로 후보 6개를 비교했다. 로컬 7B 이하 모델은 촘촘한 루브릭에서 사람과 거의 맞지 않는다는 것을 확인하고, kappa와 fail 검출까지 보고 채점기를 골랐다.
- **사람 채점도 그대로 믿지 않았다.** 불일치를 채점기 탓으로 단정하지 않고, 블라인드 재검토를 설계했다(일치 문항을 섞어 같은 사람의 재채점 일관성도 확인). 재검토 전·후 일치율을 둘 다 보고한다.
- **비용 제약 안에서 결정했다.** 무료 한도(하루 20회), 신규 사용자 모델 제한, 최소 충전액을 실측·확인하고, 자기 계열 편향 위험(OpenAI 채점기)까지 따져 선택했다.
- **모든 결정에 출처·결정자·변경 이력을 남겼다.** `evaluation/evalset/changes.csv`, 태그, manifest, 이 문서.

## 13. 로컬 실행과 다른 조합 실험 방법

README에는 데모를 띄우는 Docker 방법만 남기고, 실험을 다시 돌리거나 다른 조합을 시험하는 방법은 여기에 모아 둔다. 모든 명령은 저장소 루트에서 실행한다.

### 13-1. 로컬 설치

```bash
python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                 # API 키는 .env에 직접 입력(채팅·메신저로 옮기지 않는다)
python -m pytest -q                  # 테스트 확인
```

- 인덱스(`index/`)와 임시 결과(`output/`)는 git에 없다. 아래 명령으로 다시 만든다.
- 처음 인덱스를 만들 때 임베딩 모델을 내려받는다(bge-m3 약 2.3GB).

### 13-2. 데모 앱

```bash
python src/indexing.py               # .env 기본값(bge-m3) → index/faq_v2/bge-m3
python -m streamlit run app.py
```

- 검색 구성은 `.env`의 `EMBEDDING_PROVIDER`, `EMBEDDING_MODEL`, `CHUNKING_MODE`, `EMBEDDING_MODE`, `TOP_K`로 정한다. 인덱스를 만든 모델과 `EMBEDDING_MODEL`이 다르면 앱이 멈춘다.
- 생성 모델은 `GENERATION_PROVIDER`(`openai`, `gemini`, `ollama`)와 `GENERATION_MODEL`로 정한다.

### 13-3. 검색 실험

임베딩 모델마다 인덱스를 만들고 평가한다. 청킹(`row`, `sentence`)과 임베딩 입력(`title`, `title_body`) 조합은 한 번에 모두 평가한다(`sentence × title`은 지원하지 않음).

```bash
EMBEDDING_PROVIDER=local EMBEDDING_MODEL=BAAI/bge-m3 python src/indexing.py
EMBEDDING_PROVIDER=local EMBEDDING_MODEL=BAAI/bge-m3 python evaluation/scripts/evaluate_retrieval.py
# 여러 모델 비교표: output/retrieval_comparison.{csv,md}
python evaluation/scripts/build_retrieval_comparison.py output/retrieval_summary_<모델1>.csv output/retrieval_summary_<모델2>.csv
```

- 결과 파일: `output/retrieval_{summary,details,out_of_scope}_<모델 이름>.csv`
- 재실험의 4개 모델(`intfloat/multilingual-e5-small`, `BAAI/bge-m3`, `nlpai-lab/KURE-v1`, OpenAI `text-embedding-3-large`)은 위 두 명령에서 `EMBEDDING_PROVIDER`(`local`/`openai`)와 `EMBEDDING_MODEL`만 바꿔 실행했다.
- `sentence` 청킹은 본문을 문장 단위로 자르고(20자 미만 조각은 앞 문장에 붙임) 청크마다 FAQ 제목을 유지한다. 평가는 청크를 FAQ 연번 기준으로 중복 제거한 뒤 서로 다른 FAQ 5개(`--depth`)로 @1·@3·@5를 계산한다.
- 1차 원본 데이터로 재현: `python src/indexing.py --csv data/faq_raw.csv --output index/faq_v1/<모델 이름>` 후 평가에 `--index-dir` 지정

### 13-4. 생성 실험

검색 구성은 `.env`(또는 명령 앞 환경변수) 값을 따른다.

```bash
# A: 검색 결과 3개를 근거로 생성
GENERATION_PROVIDER=openai GENERATION_MODEL=gpt-5.4-mini python evaluation/scripts/generate_answers.py --output output/generated_answers_A_gpt-5.4-mini.csv
# B: 정답 FAQ를 근거로 생성(검색 영향 제거)
GENERATION_PROVIDER=openai GENERATION_MODEL=gpt-5.4-mini python evaluation/scripts/generate_answers.py --oracle --output output/generated_answers_B_gpt-5.4-mini_oracle.csv
# 범위 밖 질문 10개
python evaluation/scripts/generate_answers.py --questions evaluation/evalset/evalset_out_of_scope_v1.3.jsonl --output output/generated_answers_A_gpt-5.4-mini_out_of_scope.csv
```

- 중간에 멈추면 같은 명령을 다시 실행해 이어서 생성한다.
- **Ollama 모델(실험 C):** 기본 컨텍스트 2,048토큰으로는 프롬프트 앞부분이 잘리므로(8-1) 8K 모델을 만들어 쓴다.

  ```bash
  ollama pull exaone3.5:7.8b
  ollama create exaone3.5-7.8b-ctx8k -f evaluation/ollama/exaone3.5-7.8b-ctx8k.Modelfile
  GENERATION_PROVIDER=ollama GENERATION_MODEL=exaone3.5-7.8b-ctx8k python evaluation/scripts/generate_answers.py --output output/generated_answers_C_exaone3.5-7.8b.csv
  ```

  입력이 컨텍스트 한도에 닿으면 생성을 멈추고 오류를 낸다.

### 13-5. 자동 채점

```bash
python evaluation/scripts/judge_answers.py output/generated_answers_A_gpt-5.4-mini.csv --output output/judged_A.csv --judge-provider gemini
# 반복 채점 확인(일부 문항만)
python evaluation/scripts/judge_answers.py output/generated_answers_A_gpt-5.4-mini.csv --output output/rejudge_A.csv --judge-provider gemini --ids 1,5,9
```

- 채점 모델 기본값은 `gemini-3.8-flash`(8-7), `GEMINI_API_KEY`가 필요하다. 무료 등급은 프로젝트·모델당 하루 20회라 전체 채점에는 유료 등급이 필요하다(10장).
- 채점 결과를 읽지 못하면 2번 다시 요청하고, 그래도 실패하면 `error`로 따로 센다(8-2).
- 다른 채점 모델을 쓰려면 먼저 사람 채점 40문항으로 일치도를 확인한다: 같은 40문항을 채점한 뒤 `python evaluation/scripts/compare_judges.py <채점 결과 CSV들>`.
- 범위 밖 질문 답변은 자동 채점하지 않고 사람이 판정한다(`evaluation/human_review/` "범위 밖 판정").

### 13-6. 다른 조합을 시험할 때

| 바꾸는 것 | 방법 | 주의 |
|---|---|---|
| 임베딩 모델 | `EMBEDDING_MODEL`을 바꿔 13-3 실행 | 공식 사용법에 접두어가 있는 모델은 `src/indexing.py`의 `LocalEmbedder._prefix`에 추가(현재 e5만) |
| 청킹·임베딩 입력 | `CHUNKING_MODE`, `EMBEDDING_MODE` | 새 청킹 방식은 `src/indexing.py`에 추가하고 테스트 작성 |
| 검색 개수 | `TOP_K` | 생성 프롬프트 길이가 늘어나 Ollama 한도에 닿을 수 있음 |
| 생성 모델 | `GENERATION_PROVIDER`, `GENERATION_MODEL` | 같은 검색 구성·프롬프트로 A 조건과 비교. 가능하면 B(`--oracle`)도 함께 돌려 검색 탓과 생성 탓을 나눈다 |
| 생성 프롬프트 | `src/generation.py` | 프롬프트를 바꾸면 이전 결과와 직접 비교할 수 없으므로 A·B를 다시 생성 |

- 결과는 먼저 `output/`에 두고, 공개할 최종 결과만 `results/<실험 이름>/`으로 옮긴다.
- 판단 기준(148문항에서 5%p 이내면 "차이가 확인되지 않음")과 평가셋 버전(v1.3)을 바꾸지 않아야 이번 결과와 비교할 수 있다.
- 무엇을 왜 바꿨는지와 결과를 이 문서에 새 절로 남긴다.
